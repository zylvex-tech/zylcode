Executive Summary — The TL;DR

This project is an ambitious, well-governed scaffold with a real but narrow codebase, drowning in documentation debris, carrying a fabricated skeleton disguised as a feature, with a broken release pipeline, zero CI, and 91 dirty tree entries that are a divergent fork.

The good: The governance framework is exceptional — a Constitution, Architecture spec, Proof Graph, Capability Model, and an R0–R5 evidence ladder that most real companies don't have. The Agent Kernel (tool runtime, agent loop, evidence ledger, permissions, crash recovery) is real, compiles, and has 261 passing tests. The person running this project clearly understands that builders shouldn't certify their own work.

The bad: 64 root-level markdown files, 15 of which scream "COMPLETE!" for phases that were never completed. A 1,763-line "Computer-Use Engine" that is 100% fake — every action is tokio::time::sleep, every confidence is hardcoded 0.85, every screen capture is vec![0]. The intelligence module counted Rust build artifacts as "repository intelligence." The CI is blocked by a billing issue. The remote is red. The dirty tree is a divergent fork. And the product's actual tool surface (mcp.tools.yaml) isn't even tracked in git.

Phase 2A — Why It Was Rejected CRITICAL

The Phase 2A completion report claimed "Files indexed: 14,973" as evidence of repository intelligence. 14,900 of those files were Rust build artifacts under target/. The actual repository is 254 files. This happened because the exclusion list used forward-slash patterns ("/target/") on Windows, where paths use backslashes — making the exclusion dead code on the primary target platform.

The benchmark claimed "Scan duration: 12.7s" — independent re-measurement showed 276.1s (22× slower). The assertion threshold was breached. The "Acceptance Demonstration" was headed "Expected Output" — it was an expectation, not captured evidence.

The completion report was committed with Commit SHA: (Pending) and Push Verification: (Pending) — it was committed before the facts it certified were known.

3. Codebase Audit — System by System

Agent Kernel R3 — REAL

What exists: zylcode-core crate with a real tool runtime (FileSystemTool, ShellTool, GitTool, SearchTool), an iterative agent loop with AgentDecision enum (Think, Plan, ToolCall, RequestApproval, Verify, Complete, Fail), evidence ledger (append-only, hash-chained), permission gate (fail-closed, risk-classified), and crash recovery with git reconciliation.

Lines: ~643 in lib.rs, ~849 in pipeline.rs, ~346 in router/decision.rs. Real code, real tests, real behavior.

Verdict: This is the one thing that actually works. It compiles, tests pass, the agent loop executes tools and records evidence. It's not a facade.

Computer-Use Engine R0 — 100% FAKE

1,763 lines across 7 files. This is a simulation facade, not a capability. Every single function is fake:

  • Screen capture: returns vec![0; 1920 * 1080 * 4] — a buffer of zeros, 3 sites
  • Input controller: every action is tokio::time::sleep(Duration::from_millis(10-100)) — 10 sleep sites
  • Vision AI: detect_elements_internal fabricates a "Submit" button with confidence: 0.85 from image width alone. Other hardcoded confidences: 0.9, 0.95
  • GUI automation: 7 sleep-based "actions"
  • Tests: assert is_ok() against a facade that cannot fail

The code comment in mod.rs:181 literally says: "but we're testing the API with simulated success" and "In our simulated environment, this should succeed".

Only reachable surface: CLI command computer-use stats that prints zeroed counters.

Verdict: This is not a skeleton or a work-in-progress. It is a simulation that lies at the type level. A confidence: 0.85 on a hardcoded literal is not a missing feature — it is an architectural violation. The governance docs correctly say "Replace, do not extend."

Intelligence Graph R2 — REAL CODE, BROKEN METRICS

5,351 lines across 13 modules — scanner, classifier, symbols, dependency, manifest, context, query, store, entry_points, architecture, git, types. This is substantial, real code with 79 passing unit tests.

But:

  • The exclusion list is broken on Windows (forward-slash patterns on backslash paths)
  • The benchmark panics: Scan should complete in < 120s, took 276.1s
  • Not reachable from AgentLoop, CLI, or desktop app — it's a library nobody calls
  • The ignore crate was never adopted (still hand-rolled matcher)

Verdict: Real engineering buried under a Windows path bug and zero integration. The code is 90% there; the last 10% (Windows path handling, benchmark determinism, product integration) is what makes it R2 instead of R3.

Model Platform R1 — PARTIAL

Provider configuration and real HTTP dispatch exist for Anthropic, OpenAI, Google, DeepSeek, Z.AI/GLM, OpenRouter, Ollama, and a synthetic-offline provider. But capability-based routing does not exist — it's a dropdown, not "Model Democracy." Routing is not measurement-based.

Environment trap: the machine has OPENROUTER_API_KEY=YOUR_OPENROUTER_API_KEY (the literal .env.example placeholder). Tests using RouterConfig::default() egress to openrouter.ai and fail — the #1 source of false test results in this repo.

Tauri Desktop App R3 — LAUNCHES, LIMITED FUNCTION

Frontend: React + TypeScript (14 .tsx files, 9 .ts files). Components include McpInspector, ArtifactViewer, TelemetryDashboard, ProviderSettings, StatusBar, VerificationRungBadge, BridgeMonitor, ResourceGraph. 8 premium themes. The UI is polished and professional-looking.

Backend: 778 lines in main.rs. IPC commands for intent processing, streaming, tool listing, provider management, cache stats, verification.

But: the app launches and shows a window, but the core closed loop (imagine → specify → design → build → run → see → test → repair → verify → ship) does not exist. There is no Project System, no Mission Engine, no Vision Studio, no Proof Engine. The app is a monitoring dashboard for a partial agent kernel.

mcp.tools.yaml — The Product's Actual Tool Surface UNTRACKED

mcp.tools.yaml defines 30 tools with real commands (cargo check, kubectl get, sqlite3, docker, git, npm). It is loaded by default by both the MCP crate (lib.rs:73) and the Tauri app (main.rs:425,741).

It is not tracked in git. Without it, the shipped app registers zero tools. Two tools (ai.train / ai.evaluate) invoke train.py / evaluate.py which do not exist.

This is the product's actual tool surface, and it's sitting in the working tree as an untracked file, not in version control.

Final Verdict

ZylCode is a project with extraordinary governance discipline and a real but narrow codebase, sabotaged by a documentation disaster, a fake skeleton, an unpushed tree, and a broken CI pipeline. The person running this project understands evidence-first engineering better than most. The governance docs are the best thing about the project. The code that exists (Agent Kernel) is genuine and well-tested.

But the repository is in a state where an agent landing cold would be actively misled — 15 root files saying COMPLETE for things that were never completed, a 1,763-line facade pretending to be a Computer-Use Engine, 91 dirty tree entries that are a divergent fork, and the product's actual tool surface not even tracked in git.

The gap between the governance ambition and the repository reality is the defining characteristic of this project. Closing that gap — not writing new features — should be the priority. The governance framework is designed to force this. It just hasn't been followed through to the repository hygiene layer yet.
