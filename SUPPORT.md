# Support

## What ZylCode is today

ZylCode is in active development. The authoritative status of every capability is the **Public Claim
Matrix** (derived from the capability registry), not any individual message or screenshot. Status
labels follow `docs/governance/ZYLCODE_PUBLIC_COMMUNICATION_POLICY.md`:

`AVAILABLE · VERIFIED · DEVELOPER PREVIEW · IN DEVELOPMENT · PROPOSED · CONCEPT · HISTORICAL ·
SERVICE-DELIVERED`.

## Where to get help

| Need | Where |
|---|---|
| Usage question | GitHub Discussions → **Help** |
| Bug report | GitHub Issue → `bug_report` template |
| Feature idea | GitHub Discussions → **Ideas**, or Issue → `feature_request` |
| Architecture question | GitHub Discussions → **Architecture** |
| Security vulnerability | `SECURITY.md` (private, **not** a public issue) |
| Contributing process | `CONTRIBUTING.md` |

## Before asking

- Check the roadmap (`docs/roadmap/ZYLCODE_ROADMAP_V2.md`) — your question may be answered by the phase
  status.
- Check existing Discussions and Issues.
- Include: your environment (OS, `rustc --version`, app version/commit), what you did, what you expected,
  and the actual output. A report without a reproduction is slower to help with, not refused — but it
  costs everyone time.

## Scope of free support

Community support is best-effort and volunteer-driven. There is **no paid support tier active**. When a
paid support tier exists, its SLA will be stated in the commercial model and nowhere else.

## Commercial / service enquiries

Engineering and fabrication **services** (distinct from the software) are handled separately from
software support. See `zylforge.com/services` for the current service catalogue. Software support and
paid engineering services are different queues — do not conflate them.
