WHY THIS EXISTS
Phase 2A's accepted report recorded, truthfully, that symbol resolution was
regex-based and that IMPORT_RESOLVED / REFERENCE_RESOLVED were not implemented.
D1 requires them to be produced by a real resolver before those markers may be
retired. This file is the reproduction block for that change.

An independent pre-PR review rejected the first version of this evidence: it
quoted entry-level coverage as though it were the whole picture, attributed
117 partial parses to "grammar coverage" when 94 of them were one wrong grammar
selection, and left the D1 CLI demonstration cell empty. Those three things are
fixed below, along with the defects the review found in `zylcode-nav`.

No new dependency: the grammar engine is `zylcode-nav` (tree-sitter 0.25,

`zylcode-core`. The TSX grammar was already compiled and unused. Nothing here

scanner already inventories.

UPSTREAM PARSER DEFECTS FIXED (zylcode-nav)
1. TSX grammar selection. `Language::from_path` maps `.tsx` to TypeScript, and
   `parse()` selected LANGUAGE_TYPESCRIPT, so JSX could not parse. `parse()` now
   selects LANGUAGE_TSX for `.tsx`; `.ts` keeps the TypeScript grammar, and a
   `.ts` file containing JSX still reports a parse problem (tested).
   Effect: 94 partial `.tsx` files -> 24, all of which have a real cause below.
2. Rust module-directory layout. `mod decision;` in `src/router.rs` now finds
   `src/router/decision.rs`; `mod.rs`/`lib.rs`/`main.rs` keep their existing
   resolution, and a same-named file in an unrelated directory is still
   refused (negative test).
3. UTF-8 BOM. A leading BOM is skipped for parsing and every byte offset is
   shifted back, so ranges still address the file on disk; the file is never
   rewritten and no other character is stripped (tested: `start_byte == 3`).
4. The cache schema is bumped to v3. The persisted per-file facts are keyed by
   content hash, so without a bump the parser fixes above would have been
   invisible on any machine with a warm cache — which is exactly what happened
   during remediation: the first post-fix run still reported 117 partials.

WHAT THE FIXTURES PROVE
  positive/        `use crate::account::Account;` in ledger.rs resolves to
                   account.rs AND to the Account symbol, line 1; the type use
                   inside ledger.rs resolves back to that symbol.
  unsupported/     A Python file is not inventoried by the scan, and naming it
                   with resolve_file returns UNSUPPORTED_SEMANTIC_INDEX with a
                   reason — not an empty result that reads as "imports nothing".
  parse_failed/    A syntax error is reported as PARSE_PARTIAL (tree-sitter
                   recovers), every edge from that file carries from_partial.
  invalid_utf8/    An undecodable file is excluded rather than treated as empty,
                   and naming it produces an explicit refusal.

EDGE MODEL: `to_file` IS NOT ALWAYS THE SYMBOL'S FILE
157 import edges resolve their symbol into a different file from the module the
importer named — re-export chains (`pub use`). `ResolvedImport::to_file` is the
module the statement pointed at; `symbol_file` is where `to_symbol` is
declared, and is `None` when those are the same. A consumer that assumed the
symbol lived in `to_file` would be wrong 157 times in this repository, so the
distinction is a field, not a comment.

WHAT `DETERMINISTIC` DOES AND DOES NOT MEAN
Upstream `nav::Binding` carries no evidence field, so the label is asserted by
the semantic layer. For resolved files that is structural (module resolution is
path-based). For symbols, three of 1,562 resolved entries resolve to a file
holding several same-named declarations, where `nav` picks the exported match
or the first one; those three are counted in
`imports_ambiguous_symbol` and printed. The label is therefore empirical for
those edges, and the report says so rather than claiming proof.

FAIL-CLOSED TABLE — AND WHAT IS REACHABLE
  Parsed      -> clean facts
  Partial     -> PARSE_PARTIAL, edges labelled from_partial
  Failed      -> PARSE_FAILED
  Unsupported -> UNSUPPORTED_SEMANTIC_INDEX

A directory scan cannot currently produce `PARSE_FAILED`: a file whose bytes
are undecodable is dropped from inventory, and a hard parser failure is not
produced by this scanner. `PARSE_FAILED` and `UNSUPPORTED_SEMANTIC_INDEX` are
exercised through `resolve_file` (the explicit-file surface) and by the
decision-table unit test. The scan's reachable states are Parsed, Partial and
Failed-by-construction; this is stated rather than implied by a passing test.

WHAT THIS DOES NOT CLAIM
  - It does not claim D2 (test-to-code), D3 (impact), or D10 (agent/CLI
    agreement). No impact() surface exists yet, and nothing here is wired into
    AgentLoop::assemble_context.
  - It does not claim the regex extractors were removed: DEFINITION_INDEXED is
    still produced by symbols.rs, which still says so.
  - It does not claim the 33 remaining partial files are anywhere near the D1
    completeness ceiling: 29 are a grammar-version gap in
    `tree-sitter-typescript` 0.23.2, and the rest are source defects or a
    fixture. None is a resolver bug.
